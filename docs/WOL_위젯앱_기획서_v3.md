# WOL 위젯 앱 기획서 v3

> **작성일** 2026-08-14 · **문서 버전** 3.0 · **상태** 구현 착수 가능
>
> v2 대비 변경: 통신사 공유기 웹 자동화 방식 폐기 → **Pico W 에이전트 방식**으로 전환.
> PC 목록 자동 조회 / PC 전원 상태 모니터링 **범위에서 제외**. 개인 사용 목적으로 확정.

---

## 1. 개요

### 1.1 목적

안드로이드 홈 화면 위젯을 한 번 눌러 등록된 PC의 전원을 켠다. 집 안팎을 구분하지 않고 동일하게 동작한다.

### 1.2 사용 대상

**본인 및 지인 수준의 개인 사용.** 불특정 다수 배포를 전제하지 않는다.

> **이 결정이 중요한 이유**
> 불특정 다수를 대상으로 하면 "사용자마다 공유기가 다르다"는 문제를 앱이 떠안게 되어,
> 정작 본인 환경에서 확실히 동작하는 구조를 만들 수 없다. 개인 사용으로 한정함으로써
> 네트워크 구성을 고정할 수 있고, 그 결과 모든 기능이 100% 결정론적으로 동작한다.

### 1.3 핵심 설계 결정: 왜 Pico W인가

외부 네트워크에서 WOL을 하려면 인터넷에서 들어온 패킷이 LAN 내부로 **브로드캐스트**되어야 한다. 그런데,

- 대부분의 가정용 공유기는 브로드캐스트 주소(`192.168.x.255`)로의 포트포워딩을 **허용하지 않는다** (ipTIME 포함)
- 대안인 static ARP 등록은 텔넷 접근이 필요하거나 메뉴 자체가 없다
- PC가 꺼지면 공유기 ARP 캐시에서 엔트리가 사라져 유니캐스트 방식도 곧 실패한다
- SK브로드밴드 임대 공유기의 원격 WOL 페이지(`공인IP:8810`)는 **로그인에 캡차가 있어** 위젯 원탭과 근본적으로 충돌한다

**LAN 안에 상시 대기하는 소형 기기를 두면 이 문제가 전부 사라진다.** Pico W는 고정 사설 IP를 가진 평범한 기기이므로 일반 포트포워딩이 그대로 동작하고, 브로드캐스트는 Pico W가 LAN 내부에서 직접 발사한다. 공유기 기종·펌웨어·캡차와 무관해진다.

상시 켜둔 PC를 에이전트로 쓰지 않는 이유는 두 가지다. 그 PC를 끌 가능성이 있고, 무엇보다 **깨우려는 대상 자신을 에이전트로 쓸 수 없다.**

## 2. 시스템 구성

```
 [ 외부 네트워크 ]                    [ 집 LAN ]
                                     
 ┌─────────────┐   HTTP    ┌────────┐   포트     ┌─────────┐
 │  안드로이드  │ ────────► │ 공유기  │ ────────► │ Pico W  │
 │  앱 / 위젯   │           │ (SKB)  │  포워딩    │ (상시)   │
 └─────────────┘           └────────┘            └────┬────┘
                                                      │
                                          UDP 브로드캐스트 (매직패킷)
                                                      │
                                                 ┌────▼────┐
                                                 │  대상 PC │
                                                 └─────────┘
```

집 Wi-Fi 안에서는 공유기를 거치지 않고 앱이 Pico W에 직접 접속한다 (§5.3 폴백 로직).

### 2.1 구성 요소

| 구성요소 | 역할 | 비고 |
|---|---|---|
| 안드로이드 앱 | 프로필·PC 관리, 위젯 제공, 요청 전송 | 본 기획의 주 산출물 |
| Pico W 펌웨어 | HTTP 수신 → 매직패킷 발사, DDNS 갱신 | MicroPython, 단일 파일 |
| 공유기 | 포트포워딩 1건 | 설정만, 개발 대상 아님 |
| DuckDNS | 유동 공인 IP 대응 | 무료, Pico W가 자체 갱신 |

**서버·데이터베이스 없음.** Pico W 펌웨어가 기획서 v1의 "백엔드(필요하다면)" 항목을 대체한다.

## 3. 기능 범위

### 3.1 포함 (In Scope)

- 프로필 다중 등록 · 별칭 부여 · 수정 · 삭제
- PC 다중 등록 · 별칭 부여 · 수정 · 삭제 (프로필 하위)
- 앱 화면에서 PC별 전원 켜기
- 홈 화면 위젯 2종 (목록형 / 단일 아이콘형)
- 위젯 터치 시 컨펌창 (의도치 않은 WOL 방지)
- 내부망 / 외부망 자동 전환
- 프로필 · PC 정보의 암호화 로컬 저장
- 설정 화면 (앱 버전, 정보 미수집 안내, 내보내기 / 가져오기)
- 프로필 연결 테스트 (Pico W 생존 확인)

### 3.2 제외 (Out of Scope) — 의도적 배제

| 항목 | 배제 사유 |
|---|---|
| **PC 목록 자동 조회** | WOL에 목록 조회 표준이 없음. 공유기 웹 스크래핑이 유일한 방법인데 캡차·펌웨어 변경 리스크가 크고, PC 수가 적어 수동 등록으로 충분 |
| **PC 전원 상태 모니터링** | Pico W 소켓 제한·프로브 방식별 신뢰성 편차·비동기 처리 등 복잡도 대비 실익이 낮음. 위젯을 눌렀는데 안 켜지면 다시 누르면 됨 |
| **Play 스토어 출시** | 개인 계정은 테스터 12명 × 14일 비공개 테스트 통과 필요. 개인 사용 목적에 불필요 |
| **PC 원격 종료** | 대상 PC마다 별도 에이전트 설치 필요. WOL의 범위를 벗어남 |
| **iOS 대응** | 위젯 원탭 실행 모델이 다름. 안드로이드 전용 |

## 4. 데이터 모델

DB 없이 단일 JSON 문서로 관리한다.

```jsonc
{
  "version": 1,
  "profiles": [
    {
      "id": "uuid",
      "alias": "집",                          // 사용자 지정 별칭
      "internalHost": "192.168.35.50",        // 집 Wi-Fi에서 접속할 Pico W 주소
      "externalHost": "myhome.duckdns.org",   // 외부에서 접속할 주소
      "externalPort": 18080,                  // 공유기 포트포워딩 외부 포트
      "secret": "base64-encoded-32byte",      // HMAC 공유 비밀키
      "pcs": [
        {
          "id": "uuid",
          "alias": "작업PC",
          "mac": "AA:BB:CC:DD:EE:FF"
        }
      ]
    }
  ]
}
```

**설계 노트**

- `internalPort`는 80 고정 (Pico W 기본). 필요 시 필드 추가
- PC는 프로필에 **종속**된다. 프로필 삭제 시 하위 PC도 함께 삭제 (삭제 확인창에 PC 개수 표시)
- `secret`은 프로필 생성 시 앱이 자동 생성하고, 사용자는 이를 Pico W 설정에 복사한다. QR 코드 표시 기능을 두면 입력 실수를 줄일 수 있다 (선택)
- MAC 주소는 입력 시 구분자(`:`, `-`, 없음)를 자동 정규화한다

## 5. 통신 프로토콜

### 5.1 인증 방식

Pico W에서 TLS 서버를 운용하는 것은 자원상 부담이 크다. 대신 **평문 HTTP 위에서 HMAC 서명**으로 안전성을 확보한다.

```
sig = HMAC-SHA256(secret, mac + "|" + ts)
```

Pico W는 다음 조건을 모두 만족할 때만 동작한다.

1. 서명이 일치할 것
2. `ts`가 현재 시각 ±60초 이내일 것
3. 해당 `ts`가 최근 사용 이력에 없을 것 (재전송 공격 차단, 최근 32건 링버퍼)

**이 방식의 이점**: 패킷이 평문으로 노출되어도 비밀키는 유출되지 않고, 캡처한 요청을 그대로 재전송해도 통하지 않는다. 포트를 인터넷에 노출하는 위험을 실용적인 수준으로 낮춘다.

> Pico W는 RTC가 없으므로 부팅 시 NTP로 시각을 동기화해야 한다 (§6.2).

### 5.2 엔드포인트

#### `POST /wake`

```jsonc
// 요청
{ "mac": "AA:BB:CC:DD:EE:FF", "ts": 1786000000, "sig": "hex64" }

// 응답 200
{ "ok": true }

// 응답 401 — 서명 불일치 / 시각 오차 초과 / 재전송
{ "ok": false, "err": "auth" }
```

#### `GET /ping`

인증 불필요. 프로필 연결 테스트 및 내부망 판별에 사용한다.

```jsonc
{ "ok": true, "uptime": 138204, "fw": "1.0.0" }
```

### 5.3 내부망 / 외부망 자동 전환

사용자가 집인지 밖인지 의식할 필요가 없어야 한다.

```
1. internalHost 로 GET /ping  (타임아웃 300ms)
2. 200 응답 → internalHost 로 POST /wake
3. 실패/타임아웃 → externalHost:externalPort 로 POST /wake (타임아웃 5s)
4. 둘 다 실패 → 실패 토스트 + 사유 표시
```

- 집 Wi-Fi에서 외부 주소로 접속하면 NAT 루프백 미지원 시 실패하므로, **내부 주소를 반드시 먼저 시도**한다
- 300ms 타임아웃은 체감 지연이 없는 수준이며, 외부망에서는 즉시 실패하고 2단계로 넘어간다
- 위젯 탭 → 컨펌 → 전송까지 전 과정이 1초 이내여야 한다

### 5.4 전송 신뢰성

UDP는 전달을 보장하지 않으므로 **Pico W가 매직패킷을 포트 9와 7에 각각 3회, 100ms 간격으로 발사**한다. 앱은 단일 HTTP 요청만 보내면 된다.

## 6. Pico W 펌웨어 요건

MicroPython. 단일 파일 + `config.json` 구성.

### 6.1 설정 파일

```jsonc
{
  "wifi_ssid": "...",
  "wifi_pass": "...",
  "static_ip": "192.168.35.50",
  "gateway":   "192.168.35.1",
  "secret":    "앱에서 생성한 값",
  "duckdns_domain": "myhome",
  "duckdns_token":  "..."
}
```

### 6.2 필수 동작

| 항목 | 요건 |
|---|---|
| Wi-Fi 접속 | 고정 IP. 연결 실패 시 지수 백오프 재시도, 무한 루프 금지 |
| **워치독** | `machine.WDT` 활성화. 메인 루프에서 주기적 feed. **가장 중요한 요건** |
| 자동 복구 | Wi-Fi 끊김 감지 시 재연결. 5회 연속 실패 시 `machine.reset()` |
| 시각 동기화 | 부팅 시 NTP 동기화, 이후 6시간마다 재동기화 |
| HTTP 서버 | `uasyncio` 기반. 포트 80 |
| 매직패킷 | `SO_BROADCAST` 설정 후 서브넷 브로드캐스트 주소로 발사 (§5.4) |
| DDNS 갱신 | DuckDNS에 5분 주기 갱신. 실패해도 본 기능에 영향 없도록 격리 |
| 로깅 | 최근 32건 요청 이력을 메모리에 유지 (`GET /log`로 조회, 디버깅용) |

### 6.3 주의점

- **무선 격리(AP Isolation)**: Pico W는 Wi-Fi로 접속하고 대상 PC는 유선인 경우가 많다. 같은 서브넷이면 공유기가 브리지하므로 정상 동작하지만, 공유기의 무선 격리 옵션이 켜져 있거나 **게스트 네트워크**에 연결하면 브로드캐스트가 차단된다. 반드시 메인 Wi-Fi에 연결할 것
- **소켓 수 제한**: Pico W는 동시 소켓 수가 적다(5개 내외). 동시 요청을 병렬 처리하지 말고 순차 처리한다
- 전력 소비는 0.5W 내외로, 상시 가동에 부담이 없다

## 7. 안드로이드 앱 요건

### 7.1 기술 스택

| 항목 | 선택 | 사유 |
|---|---|---|
| 언어 | Kotlin | |
| UI | Jetpack Compose | |
| 위젯 | **Glance (androidx.glance.appwidget)** | Compose 문법으로 위젯 작성. RemoteViews 직접 다루는 것보다 압도적으로 단순 |
| minSdk | 31 (Android 12) | Glance 및 최신 위젯 API 활용. 개인 사용이므로 하위 호환 불필요 |
| HTTP | OkHttp | |
| 저장 | DataStore + Keystore 암호화 | §8 |
| DB | **없음** | 요건 |

### 7.2 화면 구성

#### (1) 메인 화면

- 상단: 프로필 선택 (탭 또는 드롭다운)
- 본문: 선택된 프로필의 PC 목록. 각 행에 `별칭` + `MAC(흐리게)` + **[켜기] 버튼**
- 각 행 롱프레스 → 수정 / 삭제 메뉴
- 우상단: 설정 진입
- FAB: PC 추가
- 프로필이 하나도 없을 때: 빈 상태 안내 + "프로필 추가" 유도

#### (2) 프로필 등록 / 수정 — **풀스크린 모달**

입력 항목: 별칭 / 내부 주소 / 외부 주소 / 외부 포트 / 비밀키(자동 생성, 복사 버튼)

- **[연결 테스트]** 버튼: `GET /ping`을 내부·외부 각각 시도하고 결과를 개별 표시
  - 이 기능 하나가 설정 삽질을 크게 줄여준다. 우선순위 높게 구현할 것
- 하단: 취소 / 저장

#### (3) PC 등록 / 수정 — **풀스크린 모달**

입력 항목: 별칭 / MAC 주소

- MAC 입력 형식 자동 정규화 및 유효성 검증
- 하단: 취소 / 저장

#### (4) 설정 화면

- 앱 버전
- **정보 미수집 안내** — "이 앱은 어떤 정보도 외부로 전송하거나 수집하지 않습니다. 모든 데이터는 기기 안에만 저장됩니다."
- 정보 내보내기 (§9)
- 정보 가져오기 (§9)

### 7.3 위젯

#### 목록형 위젯

- 위젯 배치 시 **구성 액티비티**에서 프로필 1개 선택
- 선택된 프로필의 PC 목록을 세로로 표시, 각 행이 곧 켜기 버튼
- 위젯 크기에 따라 표시 개수 자동 조정

#### 단일 아이콘형 위젯

- 구성 액티비티에서 프로필 → PC 순으로 선택
- 아이콘 + PC 별칭만 표시

#### 컨펌 동작 — **핵심 요건**

위젯 터치 시 **앱 본체를 실행하지 않고** 반투명 다이얼로그 액티비티만 띄운다.

```
위젯 탭 → PendingIntent → ConfirmActivity (Theme.Translucent, Dialog 스타일)
        → "작업PC를 켤까요?"  [취소] [켜기]
        → 켜기 → 요청 전송 → 토스트 후 즉시 finish()
```

- 위젯 클릭은 사용자 상호작용이므로 Android 12+ 백그라운드 액티비티 시작 제한에 걸리지 않는다. **기획서 v1의 "불가능하다면 앱을 실행한 뒤 컨펌"이라는 대안은 필요 없다**
- 컨펌창은 시스템 다이얼로그처럼 보이도록 최소한으로 구성한다
- 전송 결과는 토스트로만 알린다 (성공: "매직패킷을 보냈습니다" / 실패: 사유 표시)

## 8. 데이터 저장 및 보안

| 항목 | 방침 |
|---|---|
| 저장 위치 | 앱 내부 저장소. DataStore(Preferences) 또는 단일 JSON 파일 |
| 암호화 | **Android Keystore에 AES-256-GCM 키 생성 → JSON 전체를 암호화하여 저장** |
| 라이브러리 | `androidx.security-crypto`(EncryptedSharedPreferences)는 **deprecated이므로 사용하지 않는다.** Keystore API를 직접 사용 |
| 백업 제외 | `android:allowBackup="false"` + `dataExtractionRules`에서 제외. 클라우드 백업으로 비밀키가 새어나가지 않게 한다 |
| 평문 통신 | Pico W가 HTTP이므로 `networkSecurityConfig`에서 cleartext 허용 필요. 사설 IP·DDNS 도메인으로 범위를 좁힐 것 |
| 화면 캡처 | 비밀키 표시 화면에 `FLAG_SECURE` 적용 (선택) |
| 권한 | `INTERNET` 만 필요. **위치·저장소 권한 요구하지 않음** |

---

## 9. 내보내기 / 가져오기

### 9.1 형식

**JSON 단일 포맷.** XML·CSV는 중첩 구조 표현에 불리하므로 채택하지 않는다.

### 9.2 내보내기

1. 안내창 표시 — **"내보낸 파일에는 접속 주소와 비밀키가 포함됩니다. 타인에게 전달되지 않도록 주의하세요."**
2. 두 가지 중 선택
   - **암호화 내보내기 (기본값)** — 사용자가 입력한 암호로 파일 암호화
     `PBKDF2-HMAC-SHA256 (200,000회)` → `AES-256-GCM`
   - **비밀키 제외 내보내기** — 구조만 백업. 가져온 뒤 비밀키만 재입력
3. SAF(`ACTION_CREATE_DOCUMENT`)로 사용자가 저장 위치 지정
4. 기본 파일명: `wol-backup-YYYYMMDD.json`

> 평문 그대로 내보내는 선택지도 제공하되, 기본값으로 두지 않는다.

### 9.3 가져오기

1. SAF(`ACTION_OPEN_DOCUMENT`)로 파일 선택
2. 암호화 파일이면 암호 입력
3. **병합 / 덮어쓰기** 선택
4. 스키마 `version` 검증 후 적용, 실패 시 사유 표시

| 인터넷에 포트 노출 | 스캐닝 대상 | HMAC + 타임스탬프 + 재전송 차단 (§5.1). 비표준 포트 사용. 최악의 경우에도 피해는 "PC가 켜짐" |
| 무선 격리로 브로드캐스트 차단 | WOL 실패 | 사전 체크리스트에서 확인 |
| Windows 빠른 시작 | 종료 상태에서 WOL 실패 | 사전 체크리스트에서 해제 |
| 앱 재설치 시 데이터 소실 | 재설정 필요 | 백업 제외 정책의 반대급부. 내보내기 기능으로 대응 |

## 12. 개발 단계

### 1단계 — Pico W 펌웨어 (선행)

Wi-Fi 접속 → `POST /wake` → 매직패킷 발사 → 워치독 → NTP → HMAC 검증 → DuckDNS

**여기서 실제로 PC가 켜지는 것을 확인한 뒤 앱 개발에 착수한다.** curl 한 줄로 검증 가능하므로 앱 없이도 전체 경로를 증명할 수 있다. 순서를 바꾸면 앱과 펌웨어 중 어디가 문제인지 알 수 없게 된다.

### 2단계 — 앱 코어

데이터 모델 → 암호화 저장 → 프로필/PC CRUD 모달 → 메인 화면 → 연결 테스트 → 전송 로직(폴백 포함)

### 3단계 — 위젯

단일 아이콘형 → 컨펌 액티비티 → 목록형

### 4단계 — 설정 및 마감

설정 화면 → 내보내기/가져오기 → 아이콘 · 앱 이름 확정

---

## 13. 미확정 사항

- **앱 이름** — 미정
- **비밀키 전달 방식** — 수동 복사 / QR 코드 중 택일 (QR은 편의 기능, 후순위)
- **Pico W 사용 모델** — Pico W / Pico 2 W 중 보유 기기 기준. 요건상 차이 없음
- **다중 프로필 실사용 여부** — 현재 확정된 환경은 집 1곳. 구조는 다중을 전제하되, 2번째 환경은 Pico W를 추가 배치하면 동일하게 동작

## 부록 A. v2에서 폐기된 방안과 사유

| 폐기 방안 | 사유 |
|---|---|
| SKB 공유기 원격 WOL 페이지(`:8810`) 자동화 | **로그인에 캡차**가 있어 위젯 원탭이 성립하지 않음. 세션 쿠키 재사용도 만료 주기가 짧아 실용성 없음. 통신사 계정 정보를 앱이 다루는 구조라는 점도 부담 |
| 포트포워딩 + 유니캐스트 매직패킷 | 브로드캐스트 주소 포워딩을 대부분의 공유기가 거부. static ARP는 메뉴 부재 |
| 공유기 웹 스크래핑으로 PC 목록 자동 조회 | 펌웨어 업데이트 한 번에 전면 고장. 등록 PC 수가 적어 수동 등록 대비 실익 없음 |
| 상시 켜둔 PC를 에이전트로 사용 | 그 PC를 끌 가능성이 있고, 대상 PC 자신은 에이전트가 될 수 없음 |
| 불특정 다수 대상 배포 | 사용자별 공유기 편차를 앱이 흡수할 수 없어, 정작 본인 환경의 확실성이 떨어짐 |
